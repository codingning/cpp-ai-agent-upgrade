## 资源管理
### RAII基本概念
- RAII 是把资源的生命周期和对象的生命周期绑定，在构造函数中申请资源，在析构函数中释放资源。
  - week-01\day2_file_handle.cpp
- 为什么析构函数在错误路径下也能执行：因为C++的栈展开机制，确保了在抛出异常时，所有已经被构建的对象的析构函数都能被调用，确认资源正确释放。
### 为什么需要移动/拷贝
- 当类持有一个资源的时候，拷贝/赋值的时候，我们需要正确的处理内部资源，如果处理不正确，可能会造成double free的问题
  - day1_string.cpp
- 左值
  - 左值全部可以取地址
    - 正面：std::cout << &a 打出 000000E217CFFB50
    - 反面（#ifdef 编译期对照，一次只放一行）：
      - &10 → C2101「常量上的"&"」（字面量是纯右值，没有对象也没有存储位置）

### vector 均摊与容量（W3，09-22 闭卷独立答对）
- 扩容三件事：申请新内存 → 拷贝/移动旧元素 → 释放旧内存
  - week-03/my_vector.h push_back
- 翻倍扩容：push n 个总搬运量 S = 4+8+...+2^(k-1) = 2^k-4 = cap_-4
  - 为什么 cap_ < 2n：最后一次扩容触发条件是 cap_/2 + 1 <= n → cap_ <= 2n-2 < 2n
  - ⚠️ 前提：**至少扩容过一次**。教练实跑 n=1..100 探针：n=1、n=2 时 cap 恒为初始 4，不成立
  - 界是紧的：n=5 时 cap=8，2n-2=8，取等
- 迭代器失效：扩容 → 旧内存释放 → 全部失效；未扩容 → 只有 end 失效
  - ✅ **09-23 闭卷独立答对**（本人自己从昨天 placement new 搬运循环推出来的）
  - 实测（`iter_probe.cpp`）：`cap 4→6` 时 `v[2]` 地址 `...A898→...A9D8` 变；
    `reserve(10)` 不扩容版地址不变。⚠️ **MSVC 增长是 1.5 倍不是 2 倍**
### 容器选型：map vs unordered_map（W3，09-23 教练讲 + 实测）
- 五条「故意选更慢的 map」的理由：
  1. **有序** —— 拆成两件事：①遍历即升序 ②`lower_bound`/`upper_bound` **动态范围查询**
     - `lower_bound(X)` = 第一个 key **≥ X** 的迭代器；`upper_bound(X)` = 第一个 key **> X**；找不到返回 `end()`
     - `[lower_bound(A), upper_bound(B))` = 所有 key 落在 [A,B] 的元素
     - **unordered_map 没有这两个函数**：哈希把 key 打散进桶，桶内顺序与 key 大小无关
     - ⚠️ 只有①能靠「存完再排一次序」补上；②补不上（排序是一次性快照，插一个就作废）
  2. **迭代器稳定**（见下「迭代器失效·关联容器」）
  3. **最坏复杂度有保证** —— 红黑树最坏 O(log n)；哈希碰撞可退化 O(n)。
     key 来自外部输入且攻击者可控时 = **HashDoS**。浏览器里 URL/域名/header/cookie/DOM id 全是外部输入
     - ⚠️ HashDoS 攻击形态本身确定；**Chromium 哪个模块因此选有序容器，教练未实查，不得当结论**
  4. **key 的成本** —— 见下「key 要求」。自定义类型进 map 只欠一个 `operator<`
  5. **不需预估规模** —— unordered_map 要 `reserve` 才能避免反复 rehash
- **key 要求**（`key_probe.cpp` MSVC 实测）：
  - `std::map<K,V>`：K 要能比大小（默认 `std::less<K>` → 要 `operator<`）
  - `std::unordered_map<K,V>`：要**两样** —— `std::hash<K>` 有特化 **且** K 支持 `operator==`
    （先算 hash 定桶，桶内再逐个 `==` 比对）
  - 标准库已特化 `std::hash` 的：内置整数/浮点/指针、`std::string` 系列、**以及枚举类型**（C++14 起标准要求）
  - ✅ 实测 `unordered_map<enum class, int>` **C++17 / C++14 均编译通过**，hash=12478008331234465636
    - 📌 **教练 09-23 出错**：断言「enum class 那题其中一个编译不过」，**没跑就说，实测两边都过**，已收回
  - ❌ 实测 `unordered_map<自定义struct>` 编译失败：`xhash(118) error C2064`（无 `std::hash` 特化）
  - **q-framework 实证**：`ui/dui/Control/UIMenu.cpp:1417` 的 `std::map<CDuiString, bool>` ——
    CDuiString 是 DuiLib 自有类，`std::hash` 不认识它 → **选 map 是成本考量，不是性能考量**
### 迭代器失效 · 关联容器（W3，09-23）
- **`map`/`set`（节点式，红黑树）**：元素各自在堆上独立分配，插入不搬动别人
  - `insert` → **不失效任何迭代器**；`erase` → **只失效被删的那一个**
  - ❌ 本人 09-23 答「全部失效」，错。实测：`find(2)` 地址 `...80C40`，
    插 100 个元素 + `erase(4)` 后地址不变、值仍 20、`++it` 正常跳到下一个存活元素
  - 🔴 **09-30 第二次答错（同一点）**：本人答「insert 只导致 end 失效，erase 导致 end 和被删的失效」。
    **两处都把 `end()` 多算了一份。** 教练探针 `week-04/coach_probe_map_iter.cpp` 实跑驳回：
    三次 insert（size 3→6）后，插入前保存的 `it1`/`it3` 仍可解引用、旧 `e == m.end()` 为 **true**、
    用旧 `e` 作终止条件 `begin()` 走完 **6** 个元素；`erase(5)` 后旧 `e == m.end()` 仍为 **true**，走完 5 个。
    **根因：把 `vector` 的连续内存直觉套到节点式容器上**（`end()` 是越界哨兵，
    节点式容器里增删节点不会动它）。**知识图这一行 09-23 就写着正解，错的是索引没建起来。**
    → 复测挂 10-08（清单第 1 条，用该探针自跑后闭卷重答）
- **`unordered_map` rehash**：**使迭代器失效，但不使指向元素的指针和引用失效**
  - ⚠️ 本人 09-23 结论对（「全失效」）但理由缺，且这层区别正好被跳过
  - ✅ **09-30 独立答对，结账**：本人原话「迭代器会全部失效，指针不会失效，引用也不会失效，
    因为 unordered_map 中迭代器存储了指针和节点，rehash 以后桶发生了变化，迭代器就失效了，
    但是节点们不会失效」。**这是 09-23 答错、09-30 闭卷独立答对的一条。**
    措辞订正一处：准确说法不是「迭代器存储了指针和节点」，而是**迭代器依赖桶结构来实现 `++`**，
    桶数组重排后它走不通；节点连同 key/value 原地不动，所以指针和引用照旧有效。
  - 实测：`bucket_count 8 → 512`（真 rehash 了），但 key=2 的**元素地址前后不变**，
    用旧地址仍读出 20 → **搬的是桶数组里的指针，不是节点本身**
  - 📌 待本人核 cppreference unordered_map 页原文后销账
- **`vector::insert`**：与 `push_back` 同理 —— **扩容则全失效**；不扩容才只失效「插入点及其后」
  - ⚠️ 本人 09-23 只答了后半句。形态定名：**同一份规则在相邻两题里只用了一半**
- ✅ **09-28 结账（第三次问，允许的答法）**：`map` 慢，什么场景**故意**选它？

### 🆕 `std::string_view`（09-28 三问闭环，三版迭代）
- **它解决什么**：`void f(const std::string&)` 传字面量时编译器会**替你造一个临时 `std::string`**
  （一次堆分配 + 一次拷贝）。换成 `std::string_view` 就不造 —— 本人原话「是编译器构造的，
  构造他需要花费空间和时间，还拷贝了一份常量」。
- **所有权**：`string_view` 只有「指针 + 长度」两个字段，**不拥有数据**。
  本人原话「数据原来是谁的，谁依然拥有数据」。最大的坑是**悬垂视图**：
  底层 `std::string` 一重新分配，view 里的指针就指向已废弃的旧 buffer。
- **`\0` 问题**：`string_view::data()` **不保证以 `\0` 结尾**（本人原话「原来的数据有 `\0` 他就有，
  没有就没有」）。所以 `printf("%s", sv.data())` 会越读；正确写法 `std::cout << sv`
  或 `printf("%.*s", (int)sv.size(), sv.data())`。
- ✅ **教练实跑证据**（`week-04/string_view_probe.cpp` 第三版，`cl /utf-8 /EHsc /std:c++17` 零警告）：
  `p.data()` 从 `000000922E7CFE60`（栈上，SSO，`capacity()` = 15）跳到 `000001D76AF0F3A0`（堆上）
  → 真的重新分配了；`str` 随即打出乱码 → 悬垂视图；`std::cout << str1` 打出 `223` 正好 3 个字符，
  而上一版 `printf("%s")` 打出 32 个 —— **同一个 `string_view`，换个输出方式就正确了**，
  问题不在它身上，在怎么读它。
- ⚠️ **第一版的分辨力缺陷（本人被指出后一次改对）**：初版 `p = "222333444"` 与原串同长，
  `std::string` **原地改没换缓冲区**，看到新内容只证明 buffer 没变，不证明任何所有权的事。
  第二版本人自己想到「超过 SSO 容量（15）才会重新分配」，把 `p` 改成 33 字符，**自己逼出了悬垂**。
- 🔴 **由此新立的纪律：编译器警告不许跳过**。`printf("%p", p)` 传的是 `std::string` 对象不是 `void*`，
  MSVC 给了 4 次 `C4477`，本人跳过一整轮才发现「地址变了」是巧合（变的是栈上位置）。
  改成 `printf("%p", (void*)p.data())` 才是真证据。
- ✅ **09-29 结账**：`std::map<std::string, std::vector<Observer*>>` 遍历中调
  `o->OnPrefChanged(key)` 是虚函数 —— 若某 Observer 在里面调 `RemoveObserver`：
  **两层叠加 UB**。①**vector 层**：range-for 的 `end()` **只在进循环前求值一次**
  （C++17 标准展开 `auto __b=begin(); auto __e=end();`，教练实跑 Probe 证明 begin/end 各只调 1 次），
  erase 后缓存的 `__e` 比新 end **多一格** → 循环多读一格野内存。
  ⚠️ 此处 **cap 未变（3→3）、无重新分配，「没有扩容照样失效」**，与「扩容全失效」不是一回事。
  ②**map 层**：vector 空了会连 map 的键一起 `erase(it)`，删掉的正是循环里那个同名 `it`。
- 🔴 **重入 ≠ 并发（本人 09-29 提出，教练实跑澄清）**：调用栈
  `Notify → OnPrefChanged → Remove → vector::erase` **全在同一线程同一调用栈**，
  是**重入（reentrancy）**。**加锁不解决，还会死锁**（同线程二次进非递归 `std::mutex`）。
  数据竞争才用锁，那是另一个问题（`pref_service` 全文确实无任何锁，那个 bug 独立存在）。
- 修法两种（教练给，**未自己实现**）：①遍历副本（不需检测，低频场景够用）
  ②延迟删除打标记（Chromium `base/observer_list.h:305-319` 的做法，靠 RAII 登记活迭代器）
- ⚠️ **MSVC 陷阱（09-23 教练实跑）**：`__cplusplus` 默认返回假值 `199711L`，
  必须加 `/Zc:__cplusplus` 才是真值（实测 `201402`）。据假值推出的结论一律作废重推
### copy-and-swap（09-22 结账）
- 一个 `operator=(MyVector other)` 同时当拷贝赋值和移动赋值
  - 形参 other 在**调用点**被构造：源是左值 → 拷贝构造填它；源是右值 → 移动构造填它。函数体不知情
  - week-03/my_vector.cpp test4 实测：`b=a` → MyVector copy constructor；`b=std::move(a)` → MyVector move constructor
  - ⚠️ 分辨力提醒：`MyVector<T> e = a;` 是**初始化走构造**，不是赋值，拿它测 operator= 无效
- 强异常保证 = 可能抛的动作全部发生在碰 `*this` 之前（**不是**「出错能回滚」）
  - 手写拷贝赋值：先 delete 再 new，new 抛 bad_alloc 时旧资源已毁 → 只有基本保证
  - copy-and-swap：拷贝/移动构造发生在进函数体之前，失败时 `*this` 三个成员一个没动
  - week-03 实测：异常后 size=4 cap=4 未变，析构 8 次无泄漏，退出码 0
- swap 为什么能 noexcept：交换的是 T* 与 size_t，基本类型赋值不抛
  - noexcept 函数真抛 → std::terminate，栈展开**前**终止，外层 try/catch 接不住
- 自赋值：自己和自己交换无害，不需要 `if (this != &other)`

### 🆕 迭代器失效 · `unordered_map` rehash（10-12 结账，第三次问才独立答对）

- **本人原话**：「因为迭代器还要支持 `++` 操作，rehash 以后原来的顺序可能就发生了变化，
  所以迭代器就失效了。」
- **掉的那一环（10-10 掉，10-12 补回）**：迭代器存的是**节点指针**，
  rehash 动的只是桶数组，节点本身没搬家 —— 所以「节点变了」这个理由是错的。
  真正失效的原因是：**迭代器多承诺了「`++` 能走遍整个容器」**，
  rehash 把跨桶的遍历链重串了，**这个承诺没了**。
  裸指针从来没承诺过这个（出处 ISO `[unord.req]/9`）。
- **判据**：结论对但机制说不圆 = 没掌握。同一点连错两次（09-23、09-30），第三次独立答对才结账。

### 🆕 `string_view` 悬垂 —— 因果倒置的一个现场（10-12）

- 现象三件全对：改前打 `123456789`；把源 `string` 从 9 字符改到 33 触发重分配后打乱码；

### 🆕 `map`/`set` 的 `end()` 与 `erase`（10-12 三问全对，结账）

- **本人答**：(a) 之前拿到的 `end()` 在 insert 之后**仍然能用**；
  (b) `erase` 之后**只有指向被删元素的那个 `it` 失效**，指向其它元素的迭代器不失效。
- **机制**：`map` 是**节点式**容器，每个元素独立一个节点，
  插入删除只改链接**不搬元素** → `erase` 只销毁被删那一个节点，其余（含 `end()`）全不受影响。
  **这和 `vector` 重分配后整批失效、`unordered_map` rehash 后遍历链断，是三种完全不同的失效机制。**
- **教练实跑证据**（`std::map<int,int>`）：insert 后旧 `end()` 仍 `== m.end()`、
  `--e1` 能退到新插入的元素；`erase(2)` 后 `size=3` 返回值指向 `key=3`，
  另一个指向 `key=3` 的迭代器地址前后**完全相同**（`000001858C9A08B0`）；`erase` 也不失效 `end()`。
- 📌 实用点：`erase(it)` **有返回值**，指向被删元素的下一个 ——
  边遍历边删要写 `it = m.erase(it)`，不要自己 `++`。

### 🆕 `weak_ptr` · 两问结账（10-14，W6D3）

> 位置：接在上面 `shared_ptr` 那节之后 ——
> **`unique_ptr`（独占）→ `shared_ptr`（共享）→ `weak_ptr`（旁观）** 这条链的第三格。

- **`lock()` 为什么返回 `shared_ptr`，不返回裸指针也不返回 `bool`** —— ✅
  关键是**「检查」和「使用」之间的空隙**。若接口是 `bool alive()` + 裸指针，
  代码必然是「先问活不活 → 得到 true → 再去用」，这两步之间对象可以死掉
  （多线程另一线程释放了最后一个 `shared_ptr`；单线程中间调的函数顺手 `reset`），
  于是拿着检查通过的野指针去访问 = **use-after-free**，Chromium 高危 CVE 主力形状。
  `lock()` 在同一个原子操作里**要么把强计数 +1 并把对象交给你，要么告诉你没了** ——
  返回 `shared_ptr` 意味着「检查成功」和「拿到使用权」是同一件事，中间没有缝。
- **`expired()` vs `lock()`，为什么多线程只能用 `lock()`** —— ✅
  `expired()` 返回的是**「刚才那一瞬间活不活」**：读一次强计数判断是否为 0，
  不持有任何东西，**返回的那一刻答案就可能过期**。
  → 只能用于日志/统计/调试打印；凡「判断完要去用」一律 `if (auto sp = w.lock())`。
- **`lock()` 握住 vs 立刻丢掉 —— 本日最硬的一条（他自己用双对照组看见的）**
  教练实跑（MSVC x64 `/std:c++17 /utf-8`，`RUN_EXIT=0`）：
  | 做法 | `reset()` 之后 | `~S` 打印时机 |
  |---|---|---|
  | `auto keep = w.lock()` **握着不放** | `keep.use_count()=1`、`expired()=0` | **拖到 `keep` 出作用域**（两条分隔线之间什么都不打） |
  | `lock()` 结果**立刻丢掉** | 强计数归 0 | **`reset()` 当场打 `~S`**（打在两条分隔线之间） |
  **同一个 `reset()`，一个当场死一个不死，差别只在 `lock()` 的结果握没握住** ——
  这就是「`lock()` 把对象的命延长到你用完为止」从抽象话变成亲眼看见的事。
  🏆 分隔线对照组习惯第二天自己保持，无需提醒。
- **`weak_ptr` 为什么也是 16 字节；control block 什么时候才真正释放** —— 🟡 听讲过，待他闭卷
  不持强引用，但必须能回答「对象还活着吗」，而答案存在 **control block**（控制块）里不在对象里
  → 存**对象指针 + 控制块指针** = 8+8 = 16。控制块里至少两个计数：**强计数 + 弱计数**。
  - 强计数归 0 → **对象被析构**（`~S` 跑）
  - **但控制块不能释放**（还有 `weak_ptr` 指着它，要靠它读出「强计数=0」才能回答 `expired`）
  - 弱计数也归 0 → **控制块才释放**
  这就是为什么对象死后 `w.use_count()` 还能读到 `0` 而不崩。
  ⚠️ 工作相关：`make_shared` 把对象和控制块分配在**同一块内存**里，
  只要还有一个 `weak_ptr` 活着，**整块内存都不还给系统** —— 对象析构了、内存没释放。
  **大对象 + 长命 `weak_ptr` 是一种隐性内存占用。**

  实跑 `w4.expired()=0`（对）/ `w5.expired()=1`（**错**）→ 当时**没把两种情况分开看，

### 🆕 `variant` / `std::visit` / 结构化绑定（10-15，W6D4 · 四题全过）

**背景**：他完全没学过，按 09-28 铁律**先讲定义和答案，再让他跑实验验证**。
下面数值全部教练本机实跑（MSVC x64 `/std:c++17 /utf-8`），他的实跑结果一致。

- **`std::variant<A,B,C>`** = 类型安全的联合体（tagged union）。
  同一时刻**只装一个**成员，但**自己记着现在装的是第几个**（这就是 tag）。
  - `index()` 返回当前装的是第几个（从 0 数）。**默认构造 = `index() == 0`**（装第一个类型的默认值）。
  - `sizeof(variant<int,double,string>)` = **40**（MSVC x64）。
    = 最大成员（`std::string` 32 字节）+ 8（tag 加对齐填充）。
    **对比 `union`：`union` 不存 tag，所以不知道自己现在装的是谁** —— 这就是「类型安全」四个字的全部含义。
- **取值三个接口，错类型时反应完全不同**（这是 Q3 的靶心）：
  | 接口 | 类型对 | 类型不对 |
  |---|---|---|
  | `holds_alternative<T>(v)` | `true` | `false`（只问不取，永远安全） |
  | `get<T>(v)` | 返回值/引用 | **抛 `std::bad_variant_access`**，`what()` = `[bad variant access]` |
  | `get_if<T>(&v)` | 返回指针 | 返回 **`nullptr`**（不抛） |
  **同一次「类型不对」，一个抛异常一个返空指针** —— 选哪个取决于你想不想写 `try/catch`。
- **`std::visit`** = 把「现在装的是哪个类型」这件事交给编译器分发，
  不用自己写一串 `if (holds_alternative<...>)`。
- **结构化绑定 `auto [a,b,c] = pt;` vs `auto& [a,b,c] = pt;`**
  - 无 `&`：**先整体拷一份 `pt`**，再从副本上拆名字 → **改了不影响原对象**
  - 有 `&`：**对 `pt` 整体建一个隐藏引用**，再从它上面拆名字 → **改了直接改原对象**
  - 实跑地址：`&ra == &pt.x == ...FCB0`（同一个变量）／`&a == ...FCE0`（新变量）
- 🔴 **最咬人的一条（他 10-15 在这里栽过，挂欠账 23）**：
  **`auto& [ra,rb,rc]` 里的 `ra` 本身不是引用类型。**
  - `is_reference<decltype(ra)>` = **0**；真 `int& real_ref` 对应的值是 **1**
  - `is_same<decltype(ra), int>` = **1**（`decltype(ra)` 给 `int`，不给 `int&`）
  - 机制：标准规定结构化绑定是「对整个对象建一个隐藏引用，再给成员取名字」，
    **名字本身不是独立的引用变量**，所以 `decltype` 看不到 `&`。
  - ⚠️ **他当时拿 `&ra == &pt.x` 当「ra 是引用」的证据 —— 那个证据两种假设都成立，没分辨力。**
    能分开两种假设的是 `decltype` + `is_reference`，不是取地址。

   紧接着 `data_ = other.data_` 抄回来的是**同一个已经被释放的地址** → use-after-free。
   **正因 `delete[]` 不置空，自赋值才炸。**
3. **R6 · 布尔上下文（contextual conversion to bool）七个位置**：
   `if` / `while` / `for` 的条件、`do-while` 的条件、`!x`、`&&` `||` 的操作数、`?:` 的第一个操作数、

   - 会把这个值**当成一个 int 传出去**的位置（`int x = ptr;`、`f(int)`、`return int`）→ 拦

### ⚠️ 智能指针析构顺序（10-16 订正他的 Q4 后半，教练实跑）

他答「`unique_ptr` 才是按照构造顺序」—— **错，而且这事跟是哪种指针无关。**

实跑：三个对象 `ctor 10 / 20 / 30` → 析构打出 `dtor 30 / 20 / 10`，**逆序**。

**真分界是两个层次，别混**：

1. **栈上的指针对象**：按作用域**逆序**销毁（后声明的先死）。`unique_ptr`、`shared_ptr` 一样。
2. **堆上被管的对象**：
   - `unique_ptr` **唯一持有** → 指针一死，对象立刻跟着死
   - `shared_ptr` 有 N 个持有者 → 要**等最后一个**归 0 才死
   所以 `i=50` 先死不是「顺序」，是**持有关系** —— 它那个 `weak_ptr` 没握住，`reset()` 当场归 0。

> **生命期由谁持有决定，不由创建顺序决定。**

### ⚠️ `unique_ptr` 管 `new T[n]` 的后果订正（10-16，欠账 19 结清时改一个词）

他写「后面的成员都会泄漏」—— **「泄漏」这个词不对。**

教练实跑 `unique_ptr<Tag> p(new Tag[3])`：
`ctor 0 / ctor 1 / ctor 2` → `作用域即将结束` → `dtor 0` → **进程异常终止**（后面的 printf 没打出来）。

- **不是泄漏，是 UB**：`default_delete<T>` 调 `delete p`（单个版本），
  析构完第 0 个元素之后就去归还内存，而这块内存是 `new[]` 分配的、带数组簿记头 → 堆管理器当场终止进程。
- **泄漏 = 内存没了但程序活着；UB = 你根本不知道会发生什么。** 两个词的严重性差一档。
- **正因为是 UB 而不是可控泄漏，才必须 `delete[]`。**

## 🆕 10-19 · `std::thread` 第一课（W7D1，阶段二第一天）

> 三条定义教练按 09-28 铁律先直讲（他没学过），他跑三个实验验证。
> **实跑结论比给出的三条定义多出两层**，记在下面。

### 三条定义（给的）

1. `std::thread t(f, a, b);` —— **构造即启动**。对象一造出来，函数已在另一个线程跑了（不像 Java 要再 `start()`）。
2. `t.join()` = 当前线程停下来等它跑完；`t.detach()` = 放手不管，`t` 立刻不再关联任何线程。
3. **`std::thread` 对象析构时若既没 join 也没 detach → `std::terminate()`，进程当场死。**
   这是 C++ 标准规定，**不是 UB、不是泄漏**。

非主角概念：`std::terminate()` = 标准库的「立刻终止进程」函数，默认调 `abort()`，**不走栈展开，析构不跑**；
`joinable()` = 这个对象现在还关不关联着一个活线程。

### 实跑验收（教练实跑，`build.bat` / `cases.bat`）

| 实验 | 输出 | 退出码 |
|---|---|---|

### ❗ 增量一：`detach` 不是「安全的放手」

**它只解绑线程与进程的生命周期，不解绑线程对全局资源的依赖。**
detach 出去的线程仍然在用 `std::cout`、全局对象 —— 而这些**跟着进程走**，
main 返回后静态对象开始析构，`cout` 被销毁，那个线程还在往已析构的 `cout` 里写。

教练对照实验（只差一个变量）：

```
detach 线程里用 cout   → 连跑 10 次：崩 5 次
detach 线程不碰 cout   → 连跑 10 次：崩 0 次   （只改一个全局 volatile long long）
```

**所以 `detach` 的正确用法必须自己保证「线程不会活过它用到的资源」**，光调 `detach()` 什么都没保证。

### ❗ 增量二：退出码相同 ≠ 原因相同（本次新判据）

`test2`（detach 线程写已析构的 `cout`）与 `test3`（thread 析构未 join/detach）

| 崩溃码 | 含义 |
|---|---|
| `0xC0000409` | STATUS_STACK_BUFFER_OVERRUN / terminate、栈检查类 |
| `0xC0000005` | 访问越界（`shared_ptr` 那题遇到的是这个） |
| `0xC0000374` | 堆损坏（10-12 `unique_ptr` 管 `new T[n]` 遇到的） |
| `0xC00000FD` | 栈溢出（10-13 `make_shared` 无限递归遇到的） |

**判据：单一观察量能分开几种原因？** 退出码定不了位，要分离变量做对照组。

**并发实验里靠 sleep 对齐时序本身就是不可靠手段**，能通过不代表写对。

### 📌 传递性包含不可依赖

他用了 `std::chrono::microseconds` 却没 `#include <chrono>`，靠 `<thread>` 间接带进来，编译过了。
**自己用到的头文件自己包** —— 传递性包含在不同编译器/不同标准库版本下不保证。

### ❗ 只声明不定义的析构函数，错误会被别的错误掩盖

`week-07\day1_operatorbool.cpp` 第 10 行 `~Test();` **只有声明没有定义**。
那份文件里有三处 C2440/C2664 编译错误，**编译阶段就停了，链接器根本没运行** → 这个问题一直看不见。
教练拿掉 `explicit` 让编译通过后立刻：

```
error LNK2019: 无法解析的外部符号 "public: __cdecl Test::~Test(void)"
               (??1Test@@QEAA@XZ)，函数 "bool __cdecl test1(void)" 中引用了该符号
```

**判据：编译错误会掩盖链接错误。** 「编译不过」的文件里可能还藏着第二类问题，修完编译错误要再跑一次。
