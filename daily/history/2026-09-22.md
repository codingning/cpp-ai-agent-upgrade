### Q3 均摊推导：为什么最终 cap_ 一定小于 2n —— **独立答对**

> 因为每次扩容前的容量都是 cap，只有插入的个数超过 cap 时才会扩容，扩容后是 2*cap。
> 添加到 n 个时假设发生了 k 次扩容，总搬运 S = 4+8+16+...+2^(k-1) = 2^k-4；
> 2^k 就是现在的 cap。只有当 cap/2 装满以后才会触发最后一次扩容，
> 也就是 cap/2 + 1 <= n，即 cap <= 2n-2，也就是 cap < 2n。

- 推翻 09-21「抄答案」的判定：这次是本人自推，且抓住了**触发条件**这个关键环节
  （09-21 抄的那版正是卡在「S 与 n 之间凭什么有不等式」）。
- **教练实跑补边界**（n=1..100 探针，MSVC /std:c++17）：

  ```
  n=1  cap=4  2n-2=0   [不成立]
  n=2  cap=4  2n-2=2   [不成立]
  n=3  cap=4  2n-2=4   [成立]
  n=5  cap=8  2n-2=8   [成立，取等 → 界是紧的]
  n=100 cap=128 2n-2=198 [成立]
  ```

  n=1、n=2 时一次都没扩容，推导前提不满足。**结论须补一句「至少扩容过一次」**，否则有反例。

### Q9 copy-and-swap 为什么异常安全 —— **提示后答对**（只给一个反问即通）

先给的两条本人 09-21 已独立答对：

> 1. std::swap 对指针和整数类型的实现就是「用一个临时变量做三次赋值」，
>    全是基本类型赋值，永远不会抛异常。
> 2. noexcept 函数真抛异常，进程立即终止，不析构、不 atexit，即使外层有 try/catch
>    也接不住，因为它在栈展开前就被终止了。

第 3 问本人先答「手写的需要判断自赋值，还需要自己释放旧资源」—— 对，但还在
「代码重复」维度。教练只给一个反问（new 在哪一步、delete 在哪一步、new 抛时 delete 执行了没），
本人随即答对：

> 自己写的拷贝赋值里先 delete 释放了旧资源，然后才申请内存，如果 new 的时候异常，
> 已经执行了 delete，旧的资源也不能使用了；而 copy-and-swap 先进行了拷贝构造/移动构造
> 临时参数对象，如果失败，也没有动 this，这就是强异常保证。

- 定名：**强异常保证 = 可能抛的动作全部发生在碰 `*this` 之前**，不是「出错能回滚」。
- 补名词：noexcept 里抛异常走的是 `std::terminate`。

## 一、placement new 改造（本人自行搜索文档后完成，教练未给代码）

### 改造内容（`week-03/my_vector.h`）

| 位置 | 改前 | 改后 |
|---|---|---|
| 默认构造 | `new T[4]` | `::operator new(cap_*sizeof(T))` 只要内存 |
| 析构 | `delete[] data_` | 逐个 `data_[i].~T()` + `::operator delete` |
| 拷贝构造 | `data_[i] = other.data_[i]` | `::new (data_+i) T(other.data_[i])` |
| 扩容搬运 | `temp[i] = move_if_noexcept(...)` | `::new (temp+count) T(std::move_if_noexcept(...))` |
| push_back 写入 | `data_[size_] = v` | `::new (data_+size_) T(v)` |

### 证据 1 · 本人自建 `NO_PLACEMENT_NEW` 编译期对照（分辨力手法本人自想）

做法：给 D11 加 `std::string str` 成员，并在 `operator=` 里打印 `str`。

```
开 placement new：  D11 constructor → D11 copy constructor → D11 destructor
                    全程无 copy assignment，退出码 0

关（NO_PLACEMENT_NEW，走赋值）：
                    D11 copy assignment → 打印 str 吐乱码 → 段错误
                    退出码 139 (SIGSEGV)，崩溃前把整个进程环境变量吐到 stdout
```

- 为什么必须加 `std::string` 成员：**原来那个只打印不碰成员的 D11 对这个 bug 无分辨力**
  ——对象是否被构造过，两种假设都会打出一样的字。必须有真实持有资源的成员才照得出来。
  这条正是本人 09-20 自己总结的「实验要有分辨力」，今天自己用上了。
- 乱码 + 吐环境变量的成因：`std::string::operator=` 会读「自己原来的缓冲区指针」
  准备释放，而那块内存从没被构造过，读到的是残留垃圾。

### 证据 2 · 扩容异常安全回滚（教练三个反问后本人独立改对）

教练先只问三句（不给答案）：抛出去后 temp 谁释放、`data_[0]` 什么状态、
调用方手里的对象和调用前一样吗。本人三问全答对，其中第 3 问答出关键：

> size_，cap_ 是扩容后的值，data_ 也是被损坏的状态，和调用前不一样了。

改法（本人自写）：`count` 提到 try 外 → catch 中只析构 `[0,count)` → `::operator delete(temp)`
→ `throw;` 原样重抛；**销毁旧元素与改 `data_/cap_` 全部挪到 try 之后**；`move_if_noexcept` 加回。

教练 Boom 探针实跑（第 3 次拷贝构造时抛异常）：

```

捕获: boom

异常后继续 push 成功, size=5 cap=8
```

三条全立：`*this` 三成员未动、存活对象数进出相等、异常后对象仍可用。

## 十、【本人当日第三次在实验上推翻教练】base 与白屏的真实因果（17:5x 追加实验）

教练所给待验证结论原文：「`loadFile` 走 `file://`，`/assets/...` 会解析成磁盘根 `F:/assets/...`
→ **白屏 + 404**；修法 `vite.config.js` 加 `base: './'`」。

本人自行改 `vite.config.js` 加 `base: './'`（教练只给定位不给代码：
「base 是 defineConfig 对象的顶层属性，跟 plugins 平级」），重新 build 后双击
`dist/index.html` 用浏览器打开（`file://` 协议，与 `loadFile` 同协议），两版对照实测：

### 实测输出（本人提供）

**无 base：**
```

blocked by CORS policy: Cross origin requests are only supported for protocol schemes:

```

**有 base：**
```
Access to script at 'file:///F:/code/vite_react/vite-project/dist/assets/index-DBszTkjK.js'
from origin 'null' has been blocked by CORS policy: ...
index.html:8  GET file:///F:/code/vite_react/vite-project/dist/assets/index-DBszTkjK.js net::ERR_FAILED
index.html:9  GET file:///F:/code/vite_react/vite-project/dist/assets/index-D64VDMd1.css net::ERR_FAILED
```

`base` 生效后 src 由 `/assets/index-...js` 变为 `./assets/index-DBszTkjK.js`（本人实查）。

### 结论：教练对一半，错一半

- ✅ **路径解析部分成立**：`/assets/` 确实被解析成磁盘根 `F:/assets/`（`favicon.svg`
  那行 `ERR_FILE_NOT_FOUND` 是干净佐证），`base: './'` 确实把路径修正到了正确位置。
- ❌ **「加了 base 就不白屏」不成立 —— 两版都白屏。** 教练**漏掉了真正的拦路虎**：
  `index.html` 里的 script 带 `type="module"`，**ES 模块受 CORS 约束**，
  而 `file://` 不在浏览器允许的协议白名单内（chrome / chrome-extension / chrome-untrusted /
  data / http / https / isolated-app），直接拒绝加载，与路径对错无关。
- **路径问题与 CORS 问题是两个独立的坑**，教练只知道第一个。

### 遗留未决（教练明确标注为推测，不许当结论）

> 既然浏览器双击一定白屏，这个实验能否证明「Electron `loadFile` 也会白屏」？

教练判断：**不能证明**。理由是 Electron 渲染进程虽是 Chromium，但 Electron 对 `file://`
是否做过特殊处理、`loadFile` 与浏览器双击是否同一条路，**教练与本人目前都不知道**。
