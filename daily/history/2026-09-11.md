## 一、C++ 四问（闭卷作答 + 修正）

### 1. 如果允许 MyUniquePtr 拷贝，会发生什么灾难

我的答案：
会导致同一份资源被多个对象持有

修正补充（助手指出的缺口）：
多个持有者 → 各自析构 → 同一资源被释放多次 → UB。

### 2. `= delete` 和「不写拷贝构造」的区别

我的答案：
= delete是禁止了编译器生成拷贝构造，如果不写，编译器会自动生成

### 3. 移动构造形参为什么是 `&&` 而不是 `const&`

我的答案：
因为移动构造形参在函数里会被改变，所以不能用const 
修正（我原来的理由差在哪）：
const& 真正的问题是：它同时也能绑定左值。如果移动构造的形参是 const MyUniquePtr&，那么：

```
MyUniquePtr<Widget> a(new Widget(1));
MyUniquePtr<Widget> b = a;      // a 是左值，const& 照样能接
```
这就跟拷贝构造完全一样了——编译器无法区分"你想拷贝"和"你想移动"。

### 4. `std::move(a)` 本身做了什么

我的答案：
把资源的所属权转移给了别人。

修正（"转移所有权"这个说法哪里不准确）：
std::move(a) 本身只做了类型转换，没有转移所有权。 把左值变成了右值（static_cast<T&&>(a)）。
真正的转移发生在移动构造函数里。

## 二、三个实验

### 实验 1：拷贝灾难（`day5_badptr.cpp`）

预测：拷贝后两个对象指向同一块内存，析构两次会 double-free

实际输出：
```
[TestUniquePtr] created:   000001D9B33175E0
[TestUniquePtr] destroyed: 000001D9B33175E0    ← b 析构，delete 第一次
[TestUniquePtr] destroyed: 000001D9B33175E0    ← a 析构，delete 第二次（同一地址！）
EXIT=127
```

结论（三行地址说明了什么、退出码 127 是什么意思）：
说明了释放了同一个地址两次，导致了 UB。
退出码 127 是程序崩溃的退出码。
修正补充（助手指出的缺口）：
127 在 shell 约定里是"命令找不到"。你这里看到 127 是因为进程被 Windows 堆管理器异常终止，bash 把这个异常状态映射成了 127。真正的 Windows 错误码是 0xC0000374（STATUS_HEAP_CORRUPTION）。
### 实验 2：move-from 之后源对象的状态（`day5_move_semantics.cpp`）

| 操作 | 我的预测 | 实际结果 |
|---|---|---|
| `a->hello()` | 编译不通过 | **编译通过，运行时崩溃**（打印出前半句后炸在 `this->id`） |
| `a.reset(new Widget(200))` | 可以 reset | ✓ 正常，a 接管 Widget 200（原本为空，没有多余释放） |
| `a.release()` | 可以 release | ✓ 正常，交出裸指针后 a 置空，由调用者 `delete raw` |

实际输出：
```
Widget 100 created
Widget 200 created
Widget 200 destroyed      ← 死于 delete raw（手动释放）
Widget 100 destroyed      ← 死于 b 的析构（RAII 自动）
```
顺序对上了：200 先死（第 94 行手动 delete），100 后死（作用域结束 b 析构）。
a 最后析构时 ptr 已是 nullptr，什么都没做。

**为什么 `a->hello()` 崩溃前还能打印出 "Hello from Widget "？**
因为空指针只会在真正被解引用时才会崩溃。

具体到这个例子：`hello()` 里 `id` 其实是 `this->id`，而 `this` 就是那个 nullptr。
执行顺序是：
1. `operator->` 返回 nullptr，把 nullptr 当 this 传进 `hello()`
2. 输出字符串字面量 `"Hello from Widget "` —— 这是常量，不碰 this，安全打印
3. 求值 `this->id` —— 读 nullptr + 偏移量的地址，**炸在这一步**

**推论**：如果 `hello()` 完全不访问成员变量（比如只打印固定字符串），
`a->hello()` 很可能不崩。这就是空指针 bug 难查的原因——它潜伏到真正用成员时才爆。

### 实验 3：`return up;` 不写 std::move 能编译过吗

预测：编译失败（因为拷贝构造是 `= delete`，而 `up` 是有名字的局部变量 = 左值）

实际结果：**编译通过，正常运行**
```
Widget 2 created
Hello from Widget 2
Widget 2 destroyed
```

注释掉移动构造后的报错：
```
day5_move_semantics.cpp(99): error C2280:
  "MyUniquePtr<Widget,...>::MyUniquePtr(const MyUniquePtr<T,...> &)"：尝试引用已删除的函数
day5_move_semantics.cpp(18): note: 参见 MyUniquePtr 的声明
```
报错位置正是第 99 行 `return up;`。

**编译器的两轮机制**（注释掉移动构造后报错在第几行？说明了什么）：
能编译通过，因为编译器在返回一个局部变量的时候，因为局部变量本身是一个快消亡的变量，所以编译器认为可以随便移动，所以会优先去找移动构造函数，
如果没有移动构造函数，才会去找拷贝构造函数。

## 三、昨天遗留的三个问题（今天补验证）

### 遗留 1：函数指针 vs 模板参数存 deleter

`sizeof` 实测数据：
```
裸指针:          8
PtrA(模板参数):  16
PtrB(函数指针):  16
std::unique_ptr:  8     ← 零开销，跟裸指针一样大
```

EBO 验证：
```
sizeof(Empty)    =1
sizeof(AsMember) =16
sizeof(AsBase)   =8
```

**为什么 PtrA 是 16 而 std::unique_ptr 是 8？**
因为虽然std::default_delete<T>是一个空类，但默认大小是1字节。
对齐以后，它的大小变成了16字节。
 std::unique_ptr里把std::default_delete<T>作为基类，触发了EBO.

**模板参数相比函数指针的两个真实优势**（注意措辞，不要说成"空类占 0 字节"）：

1.模板参数能接受带捕获状态的可调用对象（lambda 捕获变量、函数对象），函数指针存不下状态。
2.模板参数是空类的时候，可以做基类，触发EBO.

### 遗留 2：函数体的 `=` 为什么是「先构造再赋值」两步

Tracer 实验输出：
```
--- 函数体赋值 ---
  默认构造          ← ① 编译器偷偷插入的（进入 { 前 t 必须已存在）
  带参构造 42       ← ② 临时对象 Tracer(42)
  赋值              ← ③ 把临时对象拷进 t，覆盖掉①
  析构              ← ④ 临时对象用完就死
  析构                   t 本身析构
（共 5 行）

--- 初始化列表 ---
  带参构造 42       ← 直接用 42 构造 t，一步到位
  析构
（共 2 行）
```

**多出来的三步分别是什么？lambda 卡在哪一步？**
1.多出来的三步是：1.调用默认构造函数 2.调用赋值运算符 3.调用析构函数。
2.lambda卡在了第一步

### 遗留 3：FILE 为什么必须自定义 deleter

`std::unique_ptr<FILE> fp(fopen(...))` 崩溃了。

**崩溃的完整因果链**：
1.因为FILE是malloc分配的，所以不能用default_delete<T>来析构。
2.所以必须自定义deleter，用fclose来析构。

**我昨天答案的两处错误**：

1.fopen 用 malloc 分配 → default_delete 用 delete 释放 → delete 释放 malloc 的内存 → 崩溃。跟"析构函数是什么"无关，是分配器不匹配。

`is_class<FILE>` 输出：1　　　→ 说明：FILE 是个 C 的 struct，而 C++ 里 struct 和 class 是同一种类型（只有默认访问权限的区别），所以它算「类」。这里推翻了我"FILE 不是类"的初判——是我判断错了。
补充：`is_destructible<FILE>` 也返回 1，说明 FILE 有一个编译器自动生成的析构函数，但它什么都不做（不会调 fclose），所以文件句柄照样泄漏。真正的问题不是"有没有析构函数"，是 delete/malloc 分配器不匹配。

## 四、今天新学的工具：type traits

`std::is_class<T>::value` / `std::is_destructible<T>::value` 是什么？

（用自己的话：它们在什么时候求值？和普通函数有什么本质区别？）
1.它们在编译时求值，而普通函数在运行时求值。
2.type traits 不是函数，是模板类（std::is_class<T> 是个类，::value 是它的静态成员常量）。所以它连"调用"都不算，纯粹是编译期的类型计算。

（可选）验证自己的 MyUniquePtr：
```cpp
std::is_copy_constructible<MyUniquePtr<Widget>>::value   // 预测： 0     实际：0
std::is_move_constructible<MyUniquePtr<Widget>>::value   // 预测： 1   实际：1
```

## 五、踩的坑

- **中文乱码（源码层）**：把 `cout` 写成了 `wcout`。原因是 `wcout` 是宽字符流，
  要配 `L"宽字符串"`；而 `"  默认构造\n"` 是窄字符串（UTF-8 字节）。
  两者不匹配，输出就乱。改回 `cout` 即可。

- **终端乱码（环境层）**：exe 在 cmd/PowerShell 里乱码但 VSCode 里正常。
  原因是 Windows 终端默认代码页是 936（GBK），拿 GBK 的表去解 UTF-8 的字节，
  自然全是乱码；VSCode 集成终端默认就是 UTF-8，所以不受影响。

  解决办法（三选一）：
  1. 临时：跑之前先执行 `chcp 65001`
  2. 一劳永逸（推荐）：在 `main` 开头加 `SetConsoleOutputCP(CP_UTF8);`
     （需 `#include <windows.h>`），程序自己设置，换终端也不怕
  3. 系统级：设置里勾选「使用 Unicode UTF-8 提供全球语言支持」（影响全局，有副作用）

## 六、今天新学的定义：左值与右值

**判断法（两条等价）：**
- 能不能对它取地址？能 → 左值
- 有没有名字？有 → 左值

```cpp
int a = 10;
&a;         // ✓ 能取地址 → a 是左值
&10;        // ✗ 报错     → 10 是右值
&(a + 1);   // ✗ 报错     → a+1 是右值（运算结果，临时的）
```

**为什么右值能安全移动**：右值马上就要消亡，掏空它不影响任何人；
左值后面可能还要用，掏空了就出事。这就是移动构造用 `&&` 的根本原因——
**用类型系统保证"只接收那些马上要死的对象"**。

**重点陷阱：`&&` 类型 ≠ 是右值。有名字就是左值，哪怕类型声明成右值引用。**

```cpp
std::string&& r = std::move(s);
check(r);              // 走【左值】重载！因为 r 有名字、能取地址
check(std::move(r));   // 这样才走右值重载
```

这条规则解释了我代码里的一个细节：
```cpp
MyUniquePtr(MyUniquePtr&& other) noexcept
    : ptr(other.ptr), deleter(std::move(other.deleter)) {
                              ^^^^^^^^^ other 是左值（有名字），
                                        不加 move 就走 deleter 的拷贝构造
}
```

**为什么 C++ 要这么设计**：如果有名字的变量自动是右值，那么
`process(x); process(x);` 第一次调用就会把 x 掏空，第二次拿到空壳，
而编译器不会警告。所以规定"有名字 = 左值 = 不会被偷偷移动"，
想移动必须显式写 `std::move`，明确表达"我知道后面不用它了"。
