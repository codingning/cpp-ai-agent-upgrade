### 6.4 🔴 CASE_MOVED_JOIN：你的理由里有两个崩因，你挑错了那一个

你写：「移动后原来的进程归 t2 管理，t1 已经空了，而 t2 没有 join，会崩溃」。
我做了三个有分辨力的对照（源码在 `%LOCALAPPDATA%\Temp\coachchk\chk.cpp` / `chk3.cpp`）：

| 实验 | 改动 | 实跑输出 |
|---|---|---|
| A_CATCH | 把你原文的 `t1.join()` 用 `try/catch(std::system_error)` 包起来，之后 `t2.join()` | 捕到 `code=22 invalid argument`，打出 `thread 1`、`normal exit`，exits `0 0 0` |
| F_HIS_EXACT_MARK | 你原文不动，`t1.join()` 前后各加一行打印 | 只打出 join **前**那行，join 后那行永远不打 |
| B_NOJOIN_SRC | 只 `t2.join()`，被 move 空的 `t1` 完全不管 | `normal exit`，exits `0 0 0` |
| C_T2_NOJOIN | 反过来：不碰 `t1`，让 `t2` 带着活线程直接析构 | `0xC0000409`，exits 三次全崩 |

1. B 证明「源对象 `t1` 被 move 空了、没人 join 它」**完全无害**，不是崩因。
2. F 证明程序崩在 `t1.join()` 这一行，没走到 main 结尾。
3. A 证明 `t1.join()` 的行为是**抛 `std::system_error`（invalid argument）**，不是直接崩；
   它变成崩，是因为**没人 catch → `std::terminate`**。`0xC0000409` 就是 MSVC 的 fail-fast。

**直接原因**：对一个 `joinable()==false` 的 `thread` 调 `join()` → 抛 `system_error` → 未捕获 → `terminate`。

### 16.4 🟡 「能改内核源码吗：CEF = 能」要加限定

**CEF 本身是个库（`libcef.dll` + 头文件），拿到的是二进制发行版，默认改不了内核。**
能改内核的前提是**你自己有那棵 Chromium 源码树并自己构建 CEF**。

实查对照（两个产品，两条路）：

```
E:\code\q-framework\third_party\cef\        → CEF 3.2704 / Chrome 51，含 src，5.3G
E:\code\browser\src\                        → 完整 Chromium 132 源码树（你每天改的）
```

**360 浏览器不是「用 CEF」，它是直接 fork 了 Chromium 自己维护。**
这个区分要紧：

| | 拿 CEF 二进制 | 自己 fork Chromium |
|---|---|---|
| 改内核源码 | ❌ 不能（只能用它暴露的 handler 接口） | ✅ 能（你每天在干的） |
| 跟官方版本 | CEF 发版节奏 | 自己 merge，自己承担 |
| 代表 | q-framework（全能压缩） | **360 浏览器** |

→ 所以 16.1 最后一行你答「360 属于 CEF 类」**结论方向对**（都是自带内核），
但更准确的说法是：**360 属于「自带内核」这一类，具体形态是 fork Chromium，不是用 CEF。**
你每天改 `content/` 这件事在 CEF 模式下是做不到的。
