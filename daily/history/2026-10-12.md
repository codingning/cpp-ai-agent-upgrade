### Q2 · `unique_ptr<T[]>` 析构差在哪 — **⚠️ 一半对，且「编译报错」是未验证断言**

- **对的一半**：「`unique_ptr<T[]>` 析构要循环释放整个数组」✅
- **错的一半**：本人报「用 `unique_ptr<T>` 去管 `unique_ptr<T[]>` 会**编译报错**」——
  **此断言错误，且本人自述「我不知道怎么写实验」，即没跑就报结论。**
- **教练实跑（三种情形分开验）**：

| 情形 | 代码 | 结果 |
|---|---|---|
| (a) `unique_ptr<T>` 管 `new T[n]` | `unique_ptr<D> p(new D[3])` | **编译通过 0 error**；运行期 `exit code -1073740940`（`0xC0000374` **STATUS_HEAP_CORRUPTION**），输出停在第一个 `D dtor` 即断 |
| (b) 两种类型互相赋值 | `unique_ptr<D> q = std::move(unique_ptr<D[]>(new D[3]))` | **C2440**：无法从 `unique_ptr<D[],default_delete<D[]>>` 转换为 `unique_ptr<D,default_delete<D>>` |
| (c) 无默认构造类型的 `new T[n]` | `unique_ptr<W> p(new W[3])`，`W` 只有 `W(int)` | **C2512**：没有合适的默认构造函数 |

- **真机理**：`unique_ptr<T>` 的 deleter 是 `default_delete<T>`，调 `delete p` 而非 `delete[] p`。
  **编译期完全不拦** —— `new D[3]` 返回 `D*`，`delete` 也收 `D*`，类型系统看不出少了 `[]`。
  → **这是运行时 UB，不是编译错误。**
- **🔴 本人错误性质判定**：本人印象中的「编译报错」大概率来源是 **(c)** ——
  拿自己的 `Widget` 试 `new Widget[3]` 撞上 C2512。
  **那是 `new T[n]` 要求 T 可默认构造，与 unique_ptr 毫无关系。**
  **把 new 的限制归因给 unique_ptr = 因果倒置，本日第 1 次。**
  （待本人确认是否如此，教练不代填。同类：09-19 一天三次 / 09-30 第 4 次 / 10-10 第 5 次）
- **缺的是分辨力**：三种情形混成一团（编译期拦截 / 运行期 UB / new 自身的限制），
  没有把它们拆成独立对照分别去撞。

### Q3 · 带自定义 deleter 后 `sizeof` 变不变 — **⚠️ 跑的是特例，结论被放大**

- 本人答「**不变**」，实测输出 `8 / 8 / 8` ✅ 本次实验本身有效（无捕获 lambda，空类被压进指针）。
- **但结论不成立为通则。** 教练实跑全表：

```
void*                                   = 8
unique_ptr<int>                         = 8
unique_ptr<int[]>                       = 8
unique_ptr + 无捕获 lambda deleter      = 8    (lambda 本身 sizeof = 1)
unique_ptr + 捕获 1 个 int 的 lambda    = 16   (lambda 本身 sizeof = 4)
unique_ptr + 函数指针 deleter           = 16   (fnptr sizeof = 8)
unique_ptr + std::function deleter      = 72
```

- **正确表述**：`sizeof` 由 **deleter 类型是否为空类**决定 —— 空类不占存储（压进指针里），
  **非空（捕获了变量）就整个 deleter 对象贴上来**，指针 8 + deleter 8 = 16。
- **缺的对照**：只摆了「无 deleter / 无捕获 deleter」两个，
  **第三个「有捕获 deleter」没摆** —— 两个对照都能产生 8，**无分辨力**（本人反复踩的坑）。

### 第 6 条 · rehash 后迭代器为何失效 —— **✅ 对，结账**

本人原话：「因为迭代器还要支持 `++` 操作，rehash 以后，原来的顺序可能就发生了变化，
所以迭代器就失效了」。

**判定对。** 这正是 09-28 答对、10-10 掉掉的那一层：
**迭代器比裸指针多承诺了「`++` 能走遍整个容器」。** rehash 把跨桶遍历链重串了，
节点没动（所以指针和引用都仍有效），但「下一个是谁」这件事变了。
出处 ISO `[unord.req]/9`。**同一点第三次问，这次独立答对，结账。**

### 第 7 条 · `string_view` 自己的例子 —— **⚠️ 三件对一件错，错在最关键那句**

教练把 `week-04/string_view_probe.cpp` 原样实跑（MSVC 14.44）：

```
p : 00000059C22FF920      ← 栈上（SSO，capacity=15）
p..capacity() : 15
str : 123456789
strlen : 9    str size : 9
p : 0000019A10DB2BE0      ← 换成 33 字符后，跑到堆上
str : ?+?·?·                ← 乱码
223
```

- 「改之前打 `123456789`」✅
- 「改之后打乱码」✅
- 「`p.data()` 地址变了」✅ 栈 `...F920` → 堆 `...2BE0`，与 09-28 那次一致
- 🔴 **「因为 string_view 自己不拥有数据，他指向原来的数据，原来的数据发生变化他就会跟着变化」—— 这句错，而且错得很要紧。**

**`str` 恰恰没有跟着变。** 它仍然指着那块**已经被释放的旧内存**（栈上那个 `...F920`）。
`p` 换到堆上去了，`str` 一无所知 —— **这叫悬垂（dangling），不是「跟着变化」。**

**分辨力检验（他自己立的判据）**：如果 `str` 真的「跟着变化」，
那第二次应该打出 `222333444555999...` 的前 9 个字符 `222333444`，
**而不是乱码**。乱码恰恰证明它**没有跟着走**。

**这是因果倒置的又一个变种，本日第 2 次**：
把「不拥有数据」这个**事实**，推成了「会跟着源数据变」这个**错误后果**。
正确后果链：不拥有 → 不管源的生死 → **源一搬家/销毁，view 就指向垃圾**。
**不是同步，是失联。**

这是 MSVC 的 SSO（短字符串优化）容量。09-28 他自己想到「超过 SSO 容量才重分配」

### 第 8 条 · `map` 的 `end()` 与 `erase` —— **✅ 三问全对，结账**

本人答：(a) 能用；(b) `it` 会失效，指向别的元素的迭代器不会失效。

**全对。** 教练实跑验证（`std::map<int,int>`）：

```
A3 insert 后  e1 == m.end() ?  1        ← 之前拿的 end() 仍然相等
A5 --e1 指向 key=7 val=70                ← 还能正常退一步走到新插入的元素
B2 erase(2) 后 size=3，返回值指向 key=3
B3 other(指向 key=3) 仍可用，val=30，地址 000001858C9A08B0 前后完全相同
B4 erase 后 endB == m2.end() ? 1        ← erase 也不失效 end()
```

机制：`map` 是**节点式**容器，每个元素独立一个节点，插入删除只改链接不搬元素。
`erase` 只销毁被删那一个节点 → **只有指向它的迭代器失效**，其余（含 `end()`）全不受影响。
📌 顺带给个实用点：`erase(it)` **有返回值**，指向被删元素的下一个 ——
边遍历边删时用 `it = m.erase(it)`，不要自己 `++`。

### 第 9 条 · `webview.h` 两问 —— 本人明说「忘记了」

按 09-28 铁律（他没掌握的 → 直接讲，不让猜），教练**实读 `webview/webview.h` 全文**后直讲
（不是凭 09-30 的记忆复述，第 1-60 行已重新抓取）：

**(1) `Create()` / `Destroy()` 为什么是 static**

实读第 39、41 行：
```cpp
static WEBVIEW_EXPORT WebView* Create();
static WEBVIEW_EXPORT void Destroy(WebView* instance);
```
`WebView` 是**纯虚基类**（第 43-53 行共 11 个 `= 0` 的纯虚函数 + 第 20-35 行嵌套的
`Delegate` 又是一个纯虚接口）。**纯虚类不能实例化** ——
没有对象，就没法用「对象.方法」的形式去造第一个对象，所以工厂必须是 static（不依赖对象存在）。
`Destroy` 配对成 static 的理由不同：**保证 new 和 delete 发生在同一个模块里**
（`WEBVIEW_EXPORT` 说明这是跨 DLL 边界的；调用方那边 delete 一个来自另一个 DLL 的对象，
堆不同会出事 —— 和你今天上午撞的堆损坏是同一类问题）。
运行期选哪个后端，靠的是第 66 行那个 `WebViewIsCefEnabled()`。

**(2) `Delegate` 干什么用的**

实读第 20-35 行，`Delegate` 里 9 个纯虚函数分两类：
- **向上问数据**：`GetSID` / `GetMID` / `GetAppVersion` / `GetAppUserDataDir` / `GetMetaData`
  —— webview 不知道这些业务信息，反过来问宿主
- **向上报事件**：`OnWebViewCreated` / `DidFinishNavigation` / `DidFailNavigation` /
  `DidTitleChange` / `DidURLChange` / `HandleAppCmd`

这是**依赖倒置**：底层的 webview 模块不去 `#include` 上层的业务头文件，
而是定义一个接口让上层来实现。实现它的类是 `WebViewWindowWin`
（09-30 他自己实查出来的，`components/ui/webview_window/win/webview_window_win.h:16`，三重继承）。

**与 Electron 对照**（这才是这条排进计划的理由）：
- `DidFinishNavigation` / `DidTitleChange` ↔ `webContents.on('did-finish-load')` / `on('page-title-updated')`
- **`HandleAppCmd(webview, module, fun, params, callback)` ↔ `ipcMain.handle` + `ipcRenderer.invoke`**
  —— 注意那个 `callback` 参数，就是 `invoke` 的那个 Promise 回传通道。
  **你下午要验的 IPC 请求-响应模式，在你自己项目里已经有一个手写版了。**
