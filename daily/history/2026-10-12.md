### Q2 · `unique_ptr<T[]>` 析构差在哪 — **⚠️ 一半对，且「编译报错」是未验证断言**

- **对的一半**：「`unique_ptr<T[]>` 析构要循环释放整个数组」✅
- **错的一半**：本人报「用 `unique_ptr<T>` 去管 `unique_ptr<T[]>` 会**编译报错**」——
  **此断言错误，且本人自述「我不知道怎么写实验」，即没跑就报结论。**
- **教练实跑（三种情形分开验）**：

| 情形 | 代码 | 结果 |
|---|---|---|
| (a) `unique_ptr<T>` 管 `new T[n]` | `unique_ptr<D> p(new D[3])` | **编译通过 0 error**；运行期 `exit code -1073740940`（`0xC0000374` **STATUS_HEAP_CORRUPTION**），输出停在第一个 `D dtor` 即断 |
| (b) 两种类型互相赋值 | `unique_ptr<D> q = std::move(unique_ptr<D[]>(new D[3]))` | **C2440**：无法从 `unique_ptr<D[],default_delete<D[]>>` 转换为 `unique_ptr<D,default_delete<D>>` |
| (c) 无默认构造类型的 `new T[n]` | `unique_ptr<W> p(new W[3])`，`W` 只有 `W(int)` | **C2512**：没有合适的默认构造函数 |

- **真机理**：`unique_ptr<T>` 的 deleter 是 `default_delete<T>`，调 `delete p` 而非 `delete[] p`。
  **编译期完全不拦** —— `new D[3]` 返回 `D*`，`delete` 也收 `D*`，类型系统看不出少了 `[]`。
  → **这是运行时 UB，不是编译错误。**
- **🔴 本人错误性质判定**：本人印象中的「编译报错」大概率来源是 **(c)** ——
  拿自己的 `Widget` 试 `new Widget[3]` 撞上 C2512。
  **那是 `new T[n]` 要求 T 可默认构造，与 unique_ptr 毫无关系。**
  **把 new 的限制归因给 unique_ptr = 因果倒置，本日第 1 次。**
  （待本人确认是否如此，教练不代填。同类：09-19 一天三次 / 09-30 第 4 次 / 10-10 第 5 次）
- **缺的是分辨力**：三种情形混成一团（编译期拦截 / 运行期 UB / new 自身的限制），
  没有把它们拆成独立对照分别去撞。

### Q3 · 带自定义 deleter 后 `sizeof` 变不变 — **⚠️ 跑的是特例，结论被放大**

- 本人答「**不变**」，实测输出 `8 / 8 / 8` ✅ 本次实验本身有效（无捕获 lambda，空类被压进指针）。
- **但结论不成立为通则。** 教练实跑全表：

```
void*                                   = 8
unique_ptr<int>                         = 8
unique_ptr<int[]>                       = 8
unique_ptr + 无捕获 lambda deleter      = 8    (lambda 本身 sizeof = 1)
unique_ptr + 捕获 1 个 int 的 lambda    = 16   (lambda 本身 sizeof = 4)
unique_ptr + 函数指针 deleter           = 16   (fnptr sizeof = 8)
unique_ptr + std::function deleter      = 72
```

- **正确表述**：`sizeof` 由 **deleter 类型是否为空类**决定 —— 空类不占存储（压进指针里），
  **非空（捕获了变量）就整个 deleter 对象贴上来**，指针 8 + deleter 8 = 16。
- **缺的对照**：只摆了「无 deleter / 无捕获 deleter」两个，
  **第三个「有捕获 deleter」没摆** —— 两个对照都能产生 8，**无分辨力**（本人反复踩的坑）。

### 第 8 条 · `map` 的 `end()` 与 `erase` —— **✅ 三问全对，结账**

### 答案（三层，层层递进）

**第一层 · 返回值（现象）**：`send` 返回 `undefined`，`invoke` 返回 `Promise`。
—— 这一层是他已经能看出来的，不是答案。

**第二层 · 多对一 vs 一对一（上面 A/B 两组的分水岭）**：
- `on` 是**事件模型**：同一个 channel 可以挂 N 个监听器，**全部都会被调用**
  （实测 `listenerCount = 2`，两个都跑了）
- `handle` 是**函数调用模型**：同一个 channel **只允许一个** handler，
  注册第二个**当场抛异常**（实测 `Attempted to register a second handler`）

**为什么必须这样**：`invoke` 要把一个值**送回去**。如果允许挂两个 handler，
那「返回哪一个的结果」就无法定义。**是「有返回值」这个需求，逼出了「只能一个 handler」这个限制。**
反过来，`send` 不需要回话，所以可以放任多个监听器各做各的事。

**第三层 · 失败语义（最容易被忽略，也是面试会挖的那层）**：
- `send` 到没人监听的 channel → **静默丢弃，什么都不发生**（实测没抛异常）
- `invoke` 到没有 handler 的 channel → **Promise reject，拿到明确错误**
  （实测 `No handler registered for ...`，且主进程侧也打了一条 `Error occurred in handler for`）

→ **`invoke` 是「通知 + 等回执 + 失败能知道」；`send` 是「发出去就不管了」。**
这不是同一件事的两种写法，**是两种不同的可靠性契约。**

### 为什么不能只留 `invoke` 一个 API

**`invoke` 永远返回 Promise，意味着调用方必须 `await` 或 `.then`。**
对「只是通知一声」的场景（点个按钮上报埋点、通知主进程写日志），
强制引入异步等待 = 白白承担一次往返延迟 + 一个需要处理 reject 的 Promise。
而且**广播型需求**（一个事件多个模块各自响应）在 `invoke` 的一对一模型里根本表达不出来。

### 回答他那个追问：你那三个为什么都选了 `handle`

教练实读 `main.cjs` 第 47-49 行：
```js

ipcMain.handle('getCurrentData', getCurrentData)
ipcMain.handle('helloName', helloName)
```
**三个全是「我要一个值」的场景** —— 选文件要文件路径、取时间要时间字符串、
`helloName` 要拼好的问候语。**`handle` 选对了，虽然当时是跟着教程选的。**

📌 **真正该记住的判据（不是"handle 更好"）**：
**看调用方要不要那个返回值。** 要 → `invoke`/`handle`；不要 → `send`/`on`。
他的 `file:pick` 如果用 `send`，渲染进程永远拿不到用户选了哪个文件 —— 功能根本不成立。
