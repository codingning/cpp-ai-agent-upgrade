## 三、未掌握 / 卡壳（教练填）

### 🔴 A. `map::insert` 迭代器失效 —— **同一点第二次答错**

本人答：「insert 只会导致 end 迭代器失效，erase 会导致 end 和删除的迭代器失效」

教练探针实跑驳回（`week-04/coach_probe_map_iter.cpp`，教练代码）：

```
三次 insert 后 size=6：
  插入前保存的 it1 解引用: 1 -> 10        ← 有效
  插入前保存的 it3 解引用: 3 -> 30        ← 有效
  插入前保存的 e == 现在的 m.end() ? true ← end 也没失效
  begin() 走到旧 e 共经过 6 个元素
erase(5) 后：it1/it3 仍可解引用，旧 e == m.end() 仍为 true
```

**正解**：`map::insert` 一个都不失效（含 end）；`erase` 只失效被删的那一个（end 不失效）。

**根因**：把 `vector` 的连续内存直觉套到节点式容器上。`map` 每个元素是独立 new 的节点，
迭代器存节点地址，插入 = 挂新节点不碰老节点。09-23 错的也是这一条。

→ 进 10-08 清单第 1 条。

### ⚠️ B. `vector::insert` 那一问答成了 `push_back`

本人答「如果没有触发扩容，it 之前的迭代器还可以使用」—— 前半对。
漏的是：`insert` 是中间插，**`it` 及之后的迭代器即使不扩容也全部失效**（元素被搬动）。
09-23 这题引用 cppreference 原文答对过，今天只答了一半。**不是不会，是答漏。**

### ⚠️ C. 标准为何写"可能失效" —— 答的是运行期条件，漏了契约层

本人答「因为不触发扩容时，有些迭代器不会失效」—— 这是 Q1 的理由。
漏掉的一层：**标准规定的是接口契约不是实现**。同一份代码 MSVC 不失效、libstdc++ 失效都合规。
对应到实际工作：Chromium 里看到"用了失效迭代器但没崩"不代表它对。
**「能跑」≠「合法」**，与 W1 学的 UB 是同一件事。

### 🔴 D. `nodeRequire` 那一问 —— **因果倒置的新变种**

本人答：「contextIsolation 被废掉了，因为这相当于网页获得了 preload 的权限，可以执行 node 了」

**层数对，机制错。** 官方文档原文（`tutorial/context-isolation`）：

> the `window` object that your preload script has access to is actually a **different** object
> than the website would have access to.

加 `nodeRequire` 并不废掉 contextIsolation —— **两个 window 照样隔离，墙还立着，
是你自己在墙上开了一扇门**。网页拿不到 preload 的 `window`，但能调你主动递过去的那个函数。
所以这实际对应**第三层（contextBridge 用错）**，不是第二层。

**新判据（本日新立，方法论）**：**「防护失效」vs「防护被绕过」是两回事。**
先问一句「这道防护本身还在工作吗」——还在工作但被自己开了后门，那是用法错不是防护失效。
这与 09-19 那三次（把隔离的手段当成隔离的理由）是同一个形状。

→ 进 10-08 清单第 2、3 条。

### ⚠️ E. `exposeInMainWorld('ipc', ipcRenderer)` 结论对，缺"为什么这就够糟"

本人答「这会导致网页可以给主进程发送任何消息」—— 与官方原文一致
（"allow any website to send arbitrary IPC messages"）。

缺的一层：**IPC 安全模型是白名单**。一个函数对应一个 IPC 消息，参数形状固定，
主进程只 handle 注册过的 channel。整个 `ipcRenderer` 暴出去 = 白名单变通用管道。
官方给的正解原文：**"provide one method per IPC message"**。
本人现有 `preload.js` 三个函数本来就是这么写的，题问的是写错会怎样。

## 六、🏆 本日质量最高的一条（本人主动顶回来的）

**本人观察推翻教练断言。**

教练说"就地改 state 会让界面慢一拍"。本人实测后顶回来：
> 「不是说只落后一次操作，我点击多少次发送按钮都没有反应，只有再次在输入框里操作时，
> 前面的才会全部显示出来，哪怕是和前一条消息不一致，也显示不出来，必须要再次操作输入框才行」

教练写探针复刻，**本人观察完全正确，教练"慢一拍"的说法是错的**。
正解：`setMessages(同引用)` 被 `Object.is` 判定无变化 → **组件函数根本没被调用**
（render 计数不涨）→ 界面无限期停留，直到碰巧有别的 state 变化才把积压的改动一起带出来。

→ **沉淀出本日最值钱的一条方法论**（已进 `docs/debt-map.md`）：
**「界面上看到什么」和「代码执行了几次」是两个独立的观察量，且工具本身还会对后者做合并显示。**
本日从三个方向撞到同一件事：
1. `setMessages(messages)` 时 DOM 不动，`render` 计数才说明组件压根没跑
2. `useEffect` 跑 2 次但 DOM 只 1 条
3. Chrome 控制台把 2 次合并成 1 行 + 一个角标

查任何"没反应/反应不对"的 bug，先确定自己观察的是哪个量。
