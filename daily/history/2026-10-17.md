### 2.4 本格踩过的坑（复盘用）

- **模板成员函数是惰性实例化的** —— 没被调用的代码不算编译过。v1 的移动赋值整个函数是文本，不是程序
- **`delete` 不置空指针** —— 与 R5 同一个坑，今天在代码里亲眼见了两次
- **拷贝赋值必须先减后加**，且必须先判自赋值，否则 use-after-free

### 3.2 R5 ✅ **过，且比昨天准确**

本人答：「死在 `delete[] data_` 这一行，因为 `delete[] data_` 不会把资源置空，后面把已经释放的资源又赋值给自己了」

**方向对，措辞需补准**。教练实跑两路（`StringBuffer` 原结构，去掉自赋值检查）：

**拷贝赋值自赋值 `a = a`：**
```
a.data() = 0000013949C131C0
delete[] 之后 data_ = 0000013949C131C0          ← 地址一个字没变
读到 other.data_ = 0000013949C149A0  len=1      ← 原来是 6
活过来了                                        ← 没崩
```
`delete[]` 那行执行完**程序活得好好的**。坏在下一行读已释放内存（use-after-free），**不崩但数据已错**（len 从 6 变 1）。

**移动赋值自赋值 `a = std::move(a)`：**
```
delete[] 执行完，data_ = 0000026321ED3140       ← 没变
赋值完，data_ = 0000000000000000
自赋值之后还活着，析构 delete[] 0000000000000000
```
`other` 是 `*this`，`other.data_ = nullptr` 等于自己置空，**6 字节泄漏，不崩**。

**结论**：`delete[]` 只「还内存」，既不置空也不报错。真正的伤害在后面那个动作——拷贝赋值是**读已释放内存**，移动赋值是**泄漏**。两种错法两个症状，`delete[]` 是起点不是终点。

**计分**：✅ 掌握。补一句要求：以后答「死在哪一行」要能说出**那行执行完之后程序是什么状态**，说不出来就是没验过。
