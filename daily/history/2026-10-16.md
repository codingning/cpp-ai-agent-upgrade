### 1.2 R1 的错（教练批改，机制已讲清）

**栈展开（stack unwinding）只是「抛异常」那条路径的名字。** 正常 `return` 出作用域、
函数走到 `}`，没有任何异常，析构照样被调用 —— 那不叫栈展开。

R1 问的「谁调用析构」正确答案：**编译器在对象生命周期结束处（作用域结束 / 临时量销毁 /
父对象析构）插入的析构调用**。栈展开是其中一个触发场景，不是机制本身。

> 📌 这条错有历史：skill 的「已掌握概念清单」里栈展开与 RAII 两条是**挨着**列的
> （「RAII：资源生命周期绑定对象生命周期」「栈展开：异常传播时栈上对象仍被析构」）。
> 39 天后两条粘成了一条 —— **典型的「索引错位」**，不是知识丢失。

### 1.3 R5 的错（本人指错位置）

本人写「前面会先释放自己的资源，**并把资源置空**」—— `delete[] data_` **不会**把
`data_` 置空，它只还内存，指针值原封不动。

**正因为它不置空，自赋值才会炸**：`delete[] data_` 之后 `other.data_`（就是
`this->data_`）已经是悬垂指针，再 `data_ = other.data_` 等于把一块已释放的内存抄回来。

→ **致命的那一行是 `delete[] data_`，不是赋值那行。赋值那行只是把尸体捡回来。**

### 1.4 R6（本人自认需要复习 → 教练直讲，不计掌握）

标准叫 **contextual conversion to bool（上下文转换）**。`explicit` 放行的完整清单只有这几个位置：

1. `if` / `while` / `for` 的条件
2. `do-while` 的条件
3. `!` 的操作数
4. `&&` 和 `||` 的操作数
5. `? :` 的第一个操作数
6. `static_assert` 的第一个参数
7. `noexcept(...)` 里的表达式

**判据（要记的是这条，不是七条清单）**：凡是**语言本身只能拿它当真假用**的位置，
`explicit` 放行；凡是**会把它当成一个值传出去**的位置（赋给 `int`、传参、`return`），
`explicit` 拦。`if(ptr)` 属前者，`int x = ptr` 属后者。

> 下次抽查形态：`return ptr;` 和 `bool b = ptr;` 哪个能过。

**Q1 教练补的量**：`lock()` 返回的 `shared_ptr` 不只是「告诉你还活着」，它**把引用计数 +1** ——
从它返回那一刻起，对象在你手里这段时间不可能被别人析构。
**`bool` 只是一张过期快照，`shared_ptr` 是一把锁。** 他在 Q3 已经说到这层，Q1 里没说出来。

**Q4 的错 —— 教练实跑三个局部 `unique_ptr`**：

```
ctor 10 / ctor 20 / ctor 30
--- 作用域即将结束 ---
dtor 30 / dtor 20 / dtor 10
```

**逆序，不是构造顺序。** 栈上局部对象一律按声明的相反顺序销毁 —— 跟 `unique_ptr` 没关系，
普通 `int`、`std::string`、他自己的 `StringBuffer` 全一样。

**真正的分界是两个层次，不是两种指针**：
- **栈上那个指针对象**什么时候死 → 看作用域，逆序。`unique_ptr` 和 `shared_ptr` 一样。
- **堆上那个被管的对象**什么时候死 → `unique_ptr` 唯一持有，指针一死对象跟着死，
  两件事看起来黏在一起；`shared_ptr` 有 N 个持有者，指针死了对象未必死。

所以 `i=50` 先死，是因为 `p7.reset()` 提前把 50 的第二个持有者丢了，而 40 那边 `p5`
一直攥着不放 —— **是持有关系决定的，不是顺序决定的。**

### 3.2 欠账 19（「调少了 vs 压根没调」）✅ 结清，一个词要改

**本人原话**：「用 `unique_ptr<T>` 管 `new T[n]`，会出现调用析构，但只析构了数组第一个成员，
**后面的成员都会泄漏**；循环引用 share_ptr 是因为到最后 share_ptr 的引用计数都不是 0，
所以根本没有调用析构」

教练实跑 `unique_ptr<Tag>` 管 `new Tag[3]`：

```

dtor 0
（进程到此终止，后面那行 printf 没打出来）
```

**不是「后面的成员泄漏」—— 是析构第一个元素之后进程就异常终止了。这是 UB，不是可控的泄漏。**

也正因为是 UB，才必须 `delete[]` —— 只有它知道该调 3 次析构。循环引用那半句对。

**五层定义**（全部从 `E:/code/browser/src` 各层 `README.md` 原文翻译，教练实查）：

| 层 | 官方定义（译） | 一句话判据 |
|---|---|---|
| `content/` | 用「多进程 + 沙箱」渲染一个页面所需的核心代码，含全部 Web 平台能力（HTML5）和 GPU 加速；**不含** Chrome 自己的功能（扩展、自动填充、拼写检查） | **任何浏览器都得有的那部分** |
| `chrome/` | Chrome 的应用层。原文特意写「`//content` 提供的是支持多个产品的框架，这个目录放的是做具体产品的代码，带主观 UX 取向」 | **Chrome 这个产品才有的那部分** |
| `components/` | 被 Chromium 一个以上的地方共用的功能/子系统（`//chrome` 与 `//ios/chrome` 共用；`//chrome` 与 `//android_webview` 共用） | **两处以上都要用，所以提出来** |
| `extensions/` | 可复用的扩展模块，实现 Chrome 扩展体系核心，**可挂在任何 content 模块的宿主上** | **扩展机制本身** |
| `net/` | Chrome 网络栈 | **网络协议/URL 那一层** |

**分层存在的理由**（`content/README.md` 动机段原文）：代码长大后功能总是挂错地方，
造成**分层违例（layering violation）**和本不该有的依赖。
> 分层违例 = 底层代码反过来依赖上层代码。举例：`content/` 里出现 `#include "chrome/..."` ——
> 违例，`content/` 不该知道 Chrome 存在。
